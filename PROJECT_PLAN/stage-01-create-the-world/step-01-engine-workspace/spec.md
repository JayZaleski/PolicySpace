## Approach
- **One Cargo workspace with two crates**, under `crates/`: `policyspace-engine` (library) and `policyspace-dev-ui` (binary `dev-ui`). The dev UI depends on the engine, and the engine has no dependency on the dev UI. Cargo would reject the reverse dependency as a cycle, so the one-way rule is enforced by the structure.
- **No external dependencies** in this Step. Nothing needs them yet, and later Steps add what they need (for example, file parsing in Step 02).
- **IDs are one generic type, `Id<K>`, with a zero-sized marker type `K` for each kind of thing.** One definition covers every kind. Ids of different kinds are different types, so mixing them up fails when the code is built. Each kind declares a human-readable label used in error messages (`"good"`, `"hex"`).
- **`NameRegistry<K>` maps text names to IDs and back, for one kind.** It hands out IDs `0, 1, 2…` in registration order. That means an ID's index can index a `Vec` directly, and iteration order is deterministic (registration order, never hash order).
- **No concrete ID kinds are defined.** Each later Step adds its own. The tests use test-only kinds.
- **The single check command is a Python script, `tools/check.py`** (standard library only, matching `tools/export_status.py`). Cargo can't chain commands on its own, and Python is already a development requirement.
- **The toolchain is pinned to exactly `1.98.1`**, with the `rustfmt` and `clippy` components, in `rust-toolchain.toml`.
- **Edition 2024** for both crates, set once at the workspace level.

### `crates/engine/src/id.rs`
Module docs must explain the ID rules from design.md: text names live in setting files; a registry turns them into numeric IDs at load time; IDs are only meaningful inside the registry (world) that created them and must never be persisted (anything saved long-term stores text names); each later Step defines its own kinds.

```rust
/// Marker trait for a kind of identified thing (good, hex, deposit, ...).
/// Implemented by zero-sized marker types, e.g. `pub enum GoodKind {}`.
pub trait IdKind: 'static {
    /// Lower-case human label used in messages, e.g. "good", "resource type".
    const LABEL: &'static str;
}

/// A compact numeric ID for one thing of kind `K`.
pub struct Id<K: IdKind> {
    index: u32,
    _kind: PhantomData<fn() -> K>,
}

impl<K: IdKind> Id<K> {
    /// Creates an ID from a raw index. Crate-private: only registries hand out IDs.
    pub(crate) fn from_index(index: u32) -> Self;
    /// The ID's position in its registry (0-based), for indexing per-kind Vecs.
    pub fn index(self) -> usize;
}
```
- Implement `Clone`, `Copy`, `PartialEq`, `Eq`, `Hash`, `PartialOrd`, `Ord`, and `Debug` **by hand**, not with `#[derive]`. Derive would add `K: Clone` (and similar) bounds that the uninhabited marker types don't satisfy. Compare, order and hash by `index` only.
- `Debug` output: `Id<{LABEL}>({index})`, for example `Id<good>(3)`.
- `PhantomData<fn() -> K>` keeps `Id<K>` `Send + Sync + Copy` whatever `K` is.

```rust
/// Two-way map between text names and IDs for one kind.
pub struct NameRegistry<K: IdKind> {
    names: Vec<String>,                // index = Id::index
    by_name: HashMap<String, Id<K>>,
}

impl<K: IdKind> NameRegistry<K> {
    /// An empty registry.
    pub fn new() -> Self;
    /// Registers `name` and returns its new ID (the next index in order).
    /// Errors with IdError::DuplicateName if `name` is already registered for this kind.
    pub fn register(&mut self, name: &str) -> Result<Id<K>, IdError>;
    /// Looks up the ID for `name`.
    /// Errors with IdError::UnknownName if `name` isn't registered.
    pub fn id(&self, name: &str) -> Result<Id<K>, IdError>;
    /// The text name for `id`.
    /// Panics with a clear message if `id` didn't come from this registry (index out of range);
    /// that is a programming error, since IDs are only valid inside their own registry.
    pub fn name(&self, id: Id<K>) -> &str;
    /// Number of registered names.
    pub fn len(&self) -> usize;
    /// True if nothing is registered.
    pub fn is_empty(&self) -> bool;
    /// All (ID, name) pairs in registration order.
    pub fn iter(&self) -> impl Iterator<Item = (Id<K>, &str)> + '_;
}
```
- Also `impl<K: IdKind> Default for NameRegistry<K>`, written by hand to avoid a `K: Default` bound (clippy's `new_without_default` requires it). Implement `Debug` by hand too, if you implement it at all.
- `register` on a failed duplicate leaves the registry unchanged.
- Converting `names.len()` to `u32` in `register`: use `u32::try_from(..).expect("...")`, with a message saying the registry exceeded `u32::MAX` names. This can't happen in practice, so a panic is acceptable.
- `register` accepts any string, including an empty one. Validating name syntax belongs to the setting loader (Step 02).

```rust
/// Errors from name lookups and registration.
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum IdError {
    /// The name was already registered for this kind.
    DuplicateName { kind: &'static str, name: String },
    /// No thing of this kind has this name.
    UnknownName { kind: &'static str, name: String },
}
```
- `kind` is `K::LABEL`.
- Implement `std::fmt::Display` and `std::error::Error` by hand, with no `thiserror`. Messages:
  - `DuplicateName`: `duplicate good name 'copper'`
  - `UnknownName`: `unknown good 'copper'`

### `tools/check.py`
- A module docstring with usage, in the style of `export_status.py`: `python tools/check.py` (or `.venv/Scripts/python tools/check.py`).
- Standard library only. It resolves the project root as `Path(__file__).resolve().parent.parent` and runs each command with `cwd` set to the root, so it works from any directory.
- It runs these commands in order, printing a header line before each:
  1. `cargo fmt --all -- --check`
  2. `cargo clippy --workspace --all-targets -- -D warnings`
  3. `cargo test --workspace`
- It runs all three even if an earlier one fails, then prints a summary (each check: passed/failed) and exits `0` only if all passed, `1` otherwise.
- If `cargo` isn't found (`FileNotFoundError` / `shutil.which("cargo")` is `None`), it prints a clear message and exits `1`.
- Commands are passed as argument lists, never through a shell string.

## Test Plan
The unit tests live in a `#[cfg(test)] mod tests` in `id.rs`, using test-only kinds such as `enum TestGood {}` (`LABEL = "good"`) and `enum TestHex {}` (`LABEL = "hex"`).

| # | Test | Acceptance Criterion |
|---|---|---|
| 1 | Registering `a`, `b`, `c` gives IDs with indices 0, 1, 2. `name(id)` returns the original text, and `id(name)` returns the same ID. | gives each registered text name an ID and turns it back into the same text name |
| 2 | `iter()` yields `(id, name)` in registration order. `len`/`is_empty` are correct before and after registering. | same |
| 3 | Registering `copper` twice for one kind returns `Err(IdError::DuplicateName { kind: "good", name: "copper" })`, and `len()` is unchanged. | rejects a duplicate text name within one kind |
| 4 | `id("missing")` returns `Err(IdError::UnknownName { kind: "good", name: "missing" })`. Its `Display` text is `unknown good 'missing'`. Also check the `DuplicateName` display text. | reports a missing text name clearly |
| 5 | A `NameRegistry<TestGood>` and a `NameRegistry<TestHex>` can both register `copper`, with no error. | allows the same text name in two different kinds |
| 6 | `name()` with an out-of-range ID panics (`#[should_panic]`; build the bad ID with `Id::from_index`, which is crate-visible in tests). | (robustness; IDs are only valid in their own registry) |
| 6a | `Id`'s `Debug` output uses the kind's label: `Id::<TestGood>::from_index(3)` formats as `Id<good>(3)`. | (checks the `Debug` format defined in Interfaces & Data) |
| 7 | A `compile_fail` doc test on `Id` (in `id.rs` docs) shows that passing an `Id<HexKind>` where an `Id<GoodKind>` is expected doesn't compile. The doc test defines its own marker kinds and uses only public API (`NameRegistry::register` to obtain IDs). | keeps different ID kinds from being mixed up (caught at build time) |

## Constraints
- Add no external crates (no `thiserror`, `serde`, etc.).
- Don't define any concrete ID kinds (goods, hexes, deposits…) in non-test code. Later Steps own them.
- The engine crate must never depend on the dev UI crate, or on any UI library.
- Determinism: anything that can be iterated must iterate in registration order. Never expose or depend on `HashMap` iteration order.
- Don't touch `PROJECT_PLAN/`, `CLAUDE.md`, `.claude/`, `manual.ipynb`, `manual.html`, `docs/`, or `tools/export_status.py`.
- Don't commit. The development loop handles commits.
- Out of scope: the setting file format and loading, world state, turns, a UI framework, CI, and save files.
